# EVM Golf: verified gas optimization of deployed contracts

## Abstract

EVM Golf lowers the execution gas of deployed EVM runtime bytecode without access
to source code. It rewrites short instruction windows and literal jumps in place,
keeping every byte offset unchanged. A change is accepted only if two independent
checks pass. First, a Lean 4 certificate, generated by the tool and checked by the
Lean kernel, proves the rewrite locally equivalent in a bounded stack and
control-flow model and binds it to the exact full bytecode. Second, revm replays
user-supplied transactions against the original and the candidate and requires
identical observable behavior and no more gas. Agents can propose their own
patches through the same gate. On 36 solc builds of OpenZeppelin, Solady and
Solmate ERC20 and ERC4626 contracts, default optimization saved 8,981 gas over
1,026 transactions. The guarantee is deliberately narrower than whole-contract
equivalence, and this paper states where it stops.

## 1. Problem

Compilers leave avoidable work in bytecode: redundant stack shuffling, constants
pushed in an inconvenient order, and jumps through one-instruction trampolines.
Removing it by hand is error prone, and a wrong rewrite can lose funds. Generic
superoptimizers rarely produce evidence a reviewer can check.

The goals are:

1. Work on deployed bytecode, including contracts whose source is unavailable.
2. Never accept a change without machine-checked evidence.
3. Let outside agents search freely while the checker stays small and fixed.
4. Be explicit about what the evidence does not cover.

## 2. Architecture

```diagram
┌──────────────┐   ┌───────────────────────┐   ┌─────────────────────────────┐
│ project.json │──▶│ candidate generation  │──▶│ acceptance gate             │
│ runtime hex  │   │  built-in rules       │   │  1. Lean certificate        │
│ scenarios    │   │  jump threading       │   │     (generated, kernel      │
└──────────────┘   │  bounded discovery    │   │      checked, 60 s budget)  │
                   │  agent proposals      │   │  2. guarded revm replay     │
                   └───────────────────────┘   └──────────────┬──────────────┘
                                                              │ both pass
                                                              ▼
                                               ┌─────────────────────────────┐
                                               │ result.json, evidence,      │
                                               │ baseline/project.json       │
                                               └─────────────────────────────┘
```

Three commands expose this:

- `inspect` prints bounded, unverified patches for each contract.
- `optimize` runs rounds of built-in rewrites, jump threading and discovery,
  sending every stage through the gate.
- `verify` sends an agent's exact patches through the gate.

A project lists contracts by id, each with deployed bytecode and a scenarios file.
A scenario is a complete local world: accounts with balance, nonce, code and
storage, a caller, the target address that receives the runtime, an optional block
environment, and an ordered list of transactions.

## 3. The fixed-layout invariant

Every accepted candidate has the same length as the original, the same instruction
boundaries outside rewritten windows, and the same JUMPDEST positions. Computed
jumps, `PC`, `CODESIZE`, jump tables and `CODECOPY` of the runtime itself therefore
keep their meaning. When a rewrite removes instructions, the freed bytes are
absorbed by widening a PUSH immediate with leading zeros. `PUSH1 0x20` becomes
`PUSH2 0x0020`: the same value, three gas either way, one byte longer.

Analysis follows fallthrough from offset 0 and treats every JUMPDEST as a possible
target, so it needs neither jump-target resolution nor global stack heights. It
rejects bytecode with operations the replay guard cannot police (DELEGATECALL,
CREATE, SELFDESTRUCT, standalone GAS and similar).

## 4. Where candidates come from

**Built-in rules.** Multiplication by 0, 1 or a power of two becomes AND, ADD or
SHL. Chains that duplicate a known zero reuse PUSH0. Two-literal AND and SHL fold
into one literal. Four fixed mask windows simplify repeated address and selector
masks.

**Jump threading.** A `PUSH X; JUMP` or `PUSH X; JUMPI` whose target `X` holds
`JUMPDEST; PUSH Y; JUMP` is retargeted to `Y` with the same PUSH width. The
trampoline stays for other callers. Each taken jump then skips JUMPDEST, PUSH and
JUMP, saving 12 gas. Sites never overlap a trampoline or a protected code read.

**Stack windows.** Discovery enumerates every sequence of up to four POP,
DUP1 to DUP8 and SWAP1 to SWAP7 instructions (69,905 raw sequences) and indexes
them by their effect on an abstract stack of eight input words, with at most two
extra slots. For every window of two to six such instructions before a PUSH, it
looks up cheaper sequences with the same effect.

**Literal placement.** One or two PUSHes inside a window are treated as opaque
words, and every cheaper enumerated placement of them among up to four stack
instructions is tried. This finds rewrites such as
`PUSH1 0x20; DUP2; SWAP1` to `DUP1; PUSH2 0x0020` and
`PUSH1 a; PUSH1 0x20; SWAP1` to `PUSH1 0x20; PUSH2 a`.

Every discovered pair is filtered by the same symbolic checker that later
generates its proof, ranked by static gas saving, and up to 32 disjoint sites form
a batch. Discovery is a bounded heuristic; the checker, not the search, decides
correctness.

**Agent proposals.** A proposal names a contract, the keccak-256 of its exact
runtime, and sites of `{original_pc, before, after}` hex windows. Proposals carry
no proofs or metadata; the checker derives everything. Windows may use PUSH, DUP,
SWAP, POP, ADD, AND, SUB and SHL, up to 64 bytes and 16 instructions.

## 5. The Lean certificate

The tool writes the Lean source itself from the two byte arrays and the site list,
then runs the pinned Lean 4.34.0 on it. No user text reaches the Lean file. The
certificate must finish within 60 seconds of wall-clock time, and its axiom report
may contain only `propext`, `Classical.choice` and `Quot.sound`, with every
expected theorem reported. Any failure or timeout rejects the candidate.

### 5.1 Local stack equivalence

`lean/Model.lean` defines a bounded word model: stack items are 256-bit vectors
and each supported opcode is a total function on the stack. For a window pair the
certificate proves:

- **Output.** For arbitrary input words, both windows leave the same stack. The
  checker first normalizes both sides symbolically (wrapping addition and
  subtraction, AND with associativity and commutativity, shifts, constant folding)
  and only emits a proof when the normal forms agree.
- **Faults.** Underflow and overflow happen at exactly the same incoming stack
  heights, 0 through 1,024, in `lean/Stack.lean`'s operational model. A generic
  lemma shows that heights far from both limits all behave alike, so only the
  boundary heights are evaluated in the kernel.
- **Context.** Substitution holds under any completely decoded prefix and suffix
  (`lean/Composition.lean`), so a window proof is not tied to an empty stack.

### 5.2 Control-flow simulation for jump threading

`lean/Threading.lean` models PUSH, JUMPDEST, JUMP and JUMPI over the full byte
list, with a list of valid destinations. Its theorem states that for every input
stack, the candidate reaches in two steps the same program counter and stack that
the original reaches after also running the trampoline, including identical
overflow and underflow outcomes. The per-site facts (opcodes, immediate values,
trampoline bytes, destination membership) are checked by the kernel on the
concrete images, the trampoline is proved unchanged, and the destination list is
proved equal to the jump destinations of both images.

### 5.3 Binding to the full bytecode

Local proofs only matter if they describe the bytes that will be deployed. Each
certificate embeds the original and the candidate as independent literals and
proves:

- sorted, disjoint sites applied to the original reconstruct the candidate exactly;
- both images decode to the same instruction rows, so lengths, boundaries and
  JUMPDEST positions agree, and sites start and end on instruction boundaries;
- constant own-code reads see identical bytes.

Deciding that two 24 KB images decode identically is slow if done naively: the
kernel took about 48 seconds on one Balancer image. The certificate instead
splits both images into the same unchanged gaps plus small site windows, proves
each split, scans every gap once as a shared term, and derives equality of the two
scans by rewriting (`lean/LayoutChunks.lean`). Together with the boundary-height
fault lemma and skipping code generation for the image literals, this cut a
24-site Balancer certificate from about 70 to about 34 seconds.

## 6. Guarded replay

Each scenario runs on two independent revm databases under Cancun rules, one with
the original runtime at the target address and one with the candidate. For every
transaction both runs must agree on success or revert, output, ordered logs, and
committed balances, nonces, storage, account existence and code hashes (except the
target's own). Exceptional halts, including out of gas, reject the candidate.
Matching reverts are allowed. Candidate receipt gas, including intrinsic gas,
refunds and the refund cap, must not be higher in any transaction.

An inspector runs in every call frame, including callbacks into the target. It
records the ordered call contexts, calldata, outcomes and returndata, every SSTORE
and TSTORE attempt and every log, including effects later rolled back, and the
candidate must reproduce the stream byte for byte. Callees must be listed fixture
accounts; ECRECOVER at address 1 must succeed in both runs; target code reads are
checked against the certified sites.

## 7. Search

`optimize` repeats, for each contract and up to a round limit:

1. built-in rewrites,
2. jump threading (only when sites exist),
3. discovery and a proposal batch.

Each stage is a full pass through the gate on the previous stage's output. A
failed proposal batch is recorded and retried with its first half; a site that
fails alone is excluded for the rest of the search. A failed threading stage is
recorded and not retried. Any other failure aborts that contract. The search stops
when a full round changes nothing or the round limit is reached, then replays the
final candidate directly against the original. Each run writes a next-baseline
project so agents can continue from accepted bytes.

## 8. What is proven, and what is not

Proven for every accepted candidate:

- The candidate is exactly the original with the listed sites changed, with
  unchanged layout and jump destinations.
- Each site is equivalent in the bounded stack model or the bounded control-flow
  model, including stack faults at every height.
- On every supplied transaction, observable behavior is identical and receipt gas
  does not increase.

Not proven:

- Behavior on inputs, states, callers or block parameters outside the scenarios.
- Behavior that depends on remaining gas. Saving gas can move an execution across
  SSTORE's 2,300-gas check or a call's gas threshold.
- Correspondence between the Lean models and revm for every opcode; the models
  erase gas and do not interpret calls, storage or memory.
- Interaction between several optimized contracts: each is checked against
  fixtures that contain the others unchanged.
- Deployment, code identity and anything that observes the code hash.

## 9. Results

Default `optimize` settings, every stage proved and replayed, no failed batches:

| Workload | Baseline | Transactions | Gas saved |
| --- | --- | ---: | ---: |
| 36 ERC20 and ERC4626 builds | solc output | 1,026 | 8,981 |
| Balancer vault token info | already optimized runtime | 23 | 219 more |
| Uniswap V3 pool, tick crossing | already optimized runtime | 37 | 228 more |
| Uniswap V3 pool, no crossing | already optimized runtime | 40 | 407 more |

The 36 builds cross three libraries, two contracts, two compiler pipelines and
three optimizer settings. Savings are execution gas: about 0.03% of the 32.7
million gas in those transactions, which is dominated by intrinsic and storage
costs. Unoptimized via-IR builds gain most, 305 to 540 gas each, mostly from jump
threading: the 36 builds contain 328 threadable jumps, 305 of them in the six
unoptimized via-IR builds. Adding jump threading raised the corpus total from 6,873
to 8,981 gas.

## 10. Limitations and next steps

**Storage access.** We looked for the obvious storage rewrites in the 38 original
contracts: a repeated SLOAD of the same symbolic slot, or an SLOAD after an SSTORE
to the same slot, inside one straight-line block with no intervening write or
call. Among 786 SLOADs and 411 SSTORES there were none; the compilers already
remove them. Useful storage savings would need cross-block analysis, for example
caching a slot read in two internal function calls, and a proof model that covers
storage, warm and cold access, refunds and reentrancy. That is future work.

**Block reordering.** Jump threading changes control flow without moving bytes.
Physically reordering basic blocks to turn jumps into fallthrough would need a
proved relocation of every jump target and is not implemented.

**Whole-contract equivalence.** A proof over all inputs would require a full EVM
semantics in Lean and a simulation proof for the whole program. The project ships
a separate developer checker for selected regions against pinned upstream EVM
semantics (`docs/dev/regions.md`), but it is not part of acceptance.

**Proof time.** The 60-second budget is wall-clock, so a heavily loaded machine can
reject valid work. Batch halving keeps progress going but does not prevent it.

## Reproducing

```sh
bash scripts/setup-lean.sh
cargo build --locked
cargo run --locked -- optimize examples/quickstart/project.json --out runs/demo
```

`bash scripts/check.sh` runs formatting, Clippy, the unit tests and the Lean-backed
tests. The benchmark contracts and fixtures are kept outside the repository.
